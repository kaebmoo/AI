## 2. สาเหตุ — ข้อเดียว อธิบายได้ทุกข้อที่ผิด

`scope` ถูกบังคับด้วยการ**ห่อทุกตารางด้วย TEMP view ที่กรองแล้ว** — โมเดลไม่เคยเห็นตัว scope
(`request_scope` ถูกอ่านเฉพาะใน `app/services/data_sources.py`; ไม่มีจุดใดใน prompt ที่พูดถึงมัน)

- **เดิม (scope = เดือนเดียว):** ทุก query ที่โมเดลเขียนถูกจำกัดที่เดือนนั้นโดยอัตโนมัติ —
  SQL ที่ "ลืมใส่เงื่อนไขงวด" ยังได้คำตอบถูก **เพราะ view มีเดือนเดียว**
- **ตอนนี้ (scope = 13–24 เดือน):** view มีสองเดือนสิงหาคม (2568 และ 2569) และ 20 งวด
  SQL เดิมที่ลืมใส่งวดจึงกลายเป็นผิดทันที

ความผิดพลาดที่เกิดจริงมีสองแบบ ทั้งคู่มาจากต้นเหตุเดียวกัน:

| แบบ | ตัวอย่าง (SQL จริงจาก `query_audit`) | ผล |
|---|---|---|
| **ไม่ใส่เงื่อนไขงวดเลย** | `SELECT SUM(revenue_ytd) … WHERE bu LIKE '%Mobile%'` (REV4) | รวม YTD ของ 20 งวด = **211,380 MB** แทน 1,358.86 |
| | `SELECT expense_group_name, SUM(…) WHERE month_no = 8 GROUP BY …` (EXP3) | รวม ส.ค. 2568 + ส.ค. 2569 = **1,911.98** แทน 944.66 (≈ 2 เท่า) |
| | `SELECT division, MAX(ebt) … GROUP BY division` (EBT6) | MAX ข้ามทุกงวด = **1,186.44** แทน 631.70 |
| **เลือกปีผิด** | `… WHERE year_month = 202508` (SAL5, SAL3, SAL4, SAL6, SAL7, SAL8, SAL10) | ตอบด้วยข้อมูล **ส.ค. 2568** ทั้งที่รายงานเป็นงวด 202608 |
| | `… WHERE time_key = 202507` (EBT7, EBT8, EBT9) | ตอบด้วย **ก.ค. 2568** |

ข้อที่ถูกภายใต้ scope กว้างคือข้อที่**ในคำถามมีปีอยู่แล้ว** ("เดือนสิงหาคม **2569**") — REV1, EXP1, SAL1 —
หรือข้อที่ถามยอดสะสมของงวดล่าสุดซึ่งบังเอิญเป็นขอบบนของ scope

**ที่ไม่ใช่สาเหตุ (ตรวจแล้ว):** ข้อมูลใน feed (ทุกตัวเลขที่ตรวจตรง control totals), contract 1.4.1 /
2.3.1 (กฎใหม่ทำงาน — ดู §3), scope enforcement (กรองถูกต้องทุกครั้ง), นโยบาย/สิทธิ, ความสดของ build

### 4.1 ที่ทำจริง — `308acb1` (เจ้าของสั่ง 2026-09-20)

`hybrid_flow.scope_note()` อ่าน `request_scope` แล้วเติมลงใน prompt **4 จุด** — คำขอที่ไม่มี scope
(chat / telegram / key เดิมทุกตัว) ได้ prompt เดิมทุกไบต์

| จุด | ทำไมต้องมี |
|---|---|
| prompt ครั้งแรก (`build_initial_user_prompt`) | ทางหลักเมื่อ two-pass ปิด |
| prompt ตอน retry | retry สร้างใหม่จากศูนย์ ไม่ได้ต่อจาก prompt เดิม |
| **pass 1 — `extract_intent`** | **จุดที่สำคัญที่สุดจริง ๆ**: `two_pass_enabled = true` บน config จริง → intent เลือกปีก่อนที่ prompt ของ SQL จะถูกสร้าง. ใส่แต่ pass 2 แล้ววัด: sales / ebt **ยังตอบจาก ส.ค. 2568 เหมือนเดิม** |
| pass 2 (`build_pass2_prompt`) | SQL ถูกเขียนที่นี่เมื่อ two-pass ทำงาน |

ข้อความที่เติม**ฉบับแรก** (`308acb1`, ตัวอย่างของรายงาน revenue งวด 2026-08) — ฉบับปัจจุบันแยกเป็น 3 กรณีมีลำดับ (§7) และบอกชื่อคอลัมน์จริงเมื่อต่างจาก key (§8):

```
**ขอบเขตข้อมูลของคำขอนี้ — ทุกตารางถูกกรองไว้แล้วเท่านี้:**
```

### 4.2 Review อิสระ (agent แยก อ่านอย่างเดียว)

ตรวจ 6 มุม: การรั่วผ่าน `llm_data_policy` · prompt ของคำขอที่ไม่มี scope · cache key · ContextVar ข้าม
request/task · scope ที่เป็นอันตราย (ชนิดปน, list 1000 ค่า) ทำให้ 500 ได้ไหม · ขอบเขตของ key ที่ออกจริง
→ **ไม่พบข้อบกพร่องที่ระดับความมั่นใจ ≥ 80** จุดสำคัญที่ผู้ตรวจยืนยันพร้อมหลักฐาน:

- `scope` เป็น**ค่าที่ผู้เรียกส่งมาเอง** ไม่ใช่ค่าที่อ่านจากแถวข้อมูล → ไม่เข้าเกณฑ์ที่ Phase 4.5 บังคับให้ผ่าน
  `restricted()`; และ `data_sources._scope_note()` ใส่คู่ key/value ชุดเดียวกันลง **system prompt** อยู่ก่อนแล้ว
  ตั้งแต่ Phase 3 — งานนี้แค่ขยายรูปแบบเดิมมาที่ user prompt
- cache key มี `scope` อยู่แล้ว และ `scope_note()` เป็น pure function ของ `scope` เท่านั้น → ไม่มีอะไรที่
  เปลี่ยนตาม request แต่ไม่อยู่ใน key (cache hit ไม่สร้าง prompt เลย)
- `request_scope` ถูก set/reset คร่อม `QueryEngine.query()` ทั้งก้อน และ task/thread ที่แตกออกไปเกิด**หลัง**
  set → ได้ค่าถูกต้องตาม semantics ของ `contextvars`; แต่ละ request เป็นคนละ Context
- scope ที่ผิดรูปถูกปฏิเสธเป็น **400 ก่อน** ถึง AI (`data_sources._literal` / `_predicate` / `scope_filters`);
  และ `scope_note()` ยังกัน `max()`/`min()` ด้วย `all(isinstance(v, int))` เองอีกชั้น → list ชนิดปนตกไปทาง `join`
- `allowed_contexts=None` **ไม่ได้แปลว่าไม่จำกัด** เมื่อมี `workspace_id`: `allowed_contexts()` คืนเซตของ
  context ใน workspace นั้น; `enforce_key_surface` จำกัด key ที่ `is_restricted()` ไว้ที่ `/api/v1/query*`
  และ `/api/v1/mcp` เท่านั้น

## 6. หมายเหตุจากการวัด

- **วัดรอบเดียวต่อเวอร์ชันของ code** — รอบยืนยันรอบสองไม่ได้ผลเพราะ (ก) revenue / expense เป็น

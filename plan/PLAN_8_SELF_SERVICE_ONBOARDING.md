## 1. ภาพที่ต้องการ (เจ้าของ 2026-09-21)

1. ลูกค้า**สมัครใช้** แล้วเริ่มใช้งาน
2. **ระบุแหล่งข้อมูลเพื่อเชื่อมต่อ** — SQL, CSV, … (อ่าน ณ ที่อยู่ ไม่ import)
3. ระบบเตรียมความพร้อม**อัตโนมัติตั้งแต่ต้นจนจบ** แล้วออก**รายงาน**ให้เจ้าของข้อมูล**ตัดสินเฉพาะสิ่งที่ระบบไม่แน่ใจ**
4. รองรับ**ทั้งสองแบบ**: ระบบอนุมานเอง (auto) และเจ้าของประกาศความหมายเอง (contract แบบ NT-Report — เจ้าของรู้ดีที่สุดว่าข้อมูลคืออะไร)
5. ถามตอบผ่าน **web GUI** · **โปรแกรมของลูกค้าเอง** (มีเอกสาร API) · **Claude Desktop** (MCP)
6. ลูกค้า**ออก API key ของตัวเอง**เพื่อเรียก `/api/v1`
7. **BYOK** — ลูกค้าใส่ key ของ LLM เอง
8. **ไม่ import ข้อมูล**ในบริการที่ใช้ร่วมกัน — import ได้เฉพาะ private deployment ที่ลูกค้าต้องการ; นอกนั้นอ่าน ณ ที่อยู่ผ่าน connector (SQL, ไฟล์; REST ภายหลัง) — **แต่การอธิบายข้อมูลยังจำเป็นเสมอ**

## 3. หลักการ (ตรึงไว้ก่อนเริ่ม)

1. **ความรู้เป็นโมเดลเดียว** — 7 ตารางของ onboarding ไม่ว่าข้อเท็จจริงจะมาจากช่องทางไหน; contract **ไม่ใช่ทางแยก** แต่เป็นหนึ่งใน input ของ pipeline เดียวกัน
2. **ทุกแถวบอกที่มา** — `declared` (contract/เจ้าของ) · `manual` (admin แก้) · `inferred` (profile + LLM) · `learned` (จากคำถามจริง) — พร้อม `confidence` และ `status` (`active` / `proposed` / `rejected`)
3. **คนชนะเครื่องเสมอ** — เครื่องไม่เขียนทับสิ่งที่คนตัดสิน (ขยายหลัก `source='manual'` ที่มีอยู่ใน `CLAUDE.md` ให้ครบทุกตาราง); ขัดกันเมื่อไร = `proposed` เข้าคิว
4. **ไม่แน่ใจ = ไม่เปิดใช้เอง** — ความมั่นใจต่ำกว่าเกณฑ์ไปอยู่ในคิว ไม่เข้า prompt จนกว่าคนจะรับ
5. **นิยาม "import" ให้ชัด** — *import* = เราถือสำเนาแถวข้อมูลเป็นที่มาของความจริง · *cache* = สิ่งที่สร้างซ้ำได้จากต้นทาง ผูกกับ build ทิ้งได้ (เช่นนิยาม view วันนี้) → บริการที่ใช้ร่วม: import **ห้าม**, cache ได้เฉพาะที่ไม่มีแถวข้อมูล · private deployment: import ได้เมื่อลูกค้าเลือก
6. **วัดคุณภาพด้วยคำถามจริง** — ชุดที่ทีมเขียนเองให้ 8/10 ขณะที่คำถามจริงของผู้ใช้ได้ 4/12 (`RESULT_F11` §7); "พร้อมใช้" ต้องวัดจากคำถามจริง + oracle ของเจ้าของข้อมูล
7. **โค้ดชุดเดียว** (D8) — ทุกความสามารถในแผนนี้ต่อ workspace; ไม่มีโค้ดเฉพาะลูกค้า

## 5. Phases

ประมาณเวลาหยาบ ๆ — ทบทวนหลังจบ 8.1

### 8.0 — ใช้เครื่องมือที่มีอยู่กับ `feed_*` ให้ครบ (1–2 วัน) — ได้ผลกับลูกค้าจริงทันที
- **ก่อนอื่น — ปี พ.ศ. ในข้อความคำตอบผิด 7 ใน 12 คำถามจริง** (`RESULT_F11` §9): SQL เลือกปีถูก แต่ขั้นอธิบายผลแปลง ค.ศ. → พ.ศ. เองแล้วผิด
  (2026 → "2566" / "2568") — ผู้ใช้อ่านตัวเลขที่ถูกเป็นของปีอื่น; **ตัวให้คะแนนต้องอ่านข้อความด้วย** ไม่ใช่แค่ `data`
- รัน `hierarchy_service.bootstrap_from_view` กับ 4 context ของ `feed_*` (อ่าน file source ได้อยู่แล้ว) → เจ้าของตรวจ
- เปิดประตู `if value_matches:` ใน `hybrid_flow.py` — วันนี้การตรวจระดับชั้นทำงานเฉพาะเมื่อ value lookup เจอค่า คำถามอย่าง "รายได้ บริการ 10 อันดับแรก" จึงไม่ได้ใช้ hierarchy แม้จะมี
- `unmatched_keywords` ของ `feed_*` 39 คำ → semantic mapping สถานะ `proposed` → เจ้าของตรวจ
- **Exit:** คำถามจริงของ portal (ชุด §7/§9 ของ `RESULT_F11` + ที่เข้ามาใหม่) **ถูกทั้งตัวเลขและปีในข้อความ** — จากฐาน 4/12 —
  และ eval ของ legacy ไม่ลด
  (แก้ประตูกระทบ legacy ด้วย → วัดทั้งสองฝั่ง)

### 8.1 — โมเดลความรู้: ที่มา + ความมั่นใจ + สถานะ (2–3 วัน) — ฐานของทุกอย่างที่ตามมา
- `source` / `confidence` / `status` ครบทั้ง 7 ตาราง (บางตารางมี `source` อยู่แล้ว — ทำให้เป็นชุดค่าเดียวกัน)
- ตัวเขียนทุกตัว (onboarding, `datafeed_knowledge`, hierarchy, ตัวเรียนรู้) ผ่านกฎเดียว: เครื่องไม่ทับคน, ขัดกัน = `proposed`
- prompt ใช้เฉพาะ `active`
- **Exit:** รันตัวเติมทุกตัวซ้ำสองรอบ → แถวของคน (`declared` / `manual`) ไม่เปลี่ยนแม้แต่ตัวเดียว (test)
- ✅ **ผล (2026-09-21, บนสำเนา):** 9 ตาราง (รวม `vanna_documentation`) มี `source` / `status` / `confidence` + คิว `knowledge_proposals` สำหรับข้อเสนอที่ชนแถวเดิม (UNIQUE ในตัวตาราง — ข้อตัดสินของเจ้าของ) · ตัวเขียนทุกตัวผ่าน `app/services/provenance.py` · ตัวอ่านที่ถึง prompt / RAG / routing / สิทธิ์ของ key กรอง `active` + server ไม่ยอมเริ่มถ้า DB ยังไม่ migrate · ตัวเติมรันสองรอบแถวของคนไม่เปลี่ยน (test) · prompt เท่าเดิมทุกไบต์เมื่อทุกแถว active (ยกเว้นกฎข้อ 5 ที่แก้ตั้งใจ) · pytest 1161 · คำถามจริง 8/12 สองรอบ · legacy 7–8/37 = base วันเดียวกัน · ค่าคงที่ในตัวอย่างของ prompt อธิบายผลแก้แล้วทำให้ P11 หลุด → ถอย, ยังค้าง (RESULT §13)

### 8.2 — Pipeline เดียว ทุก source ทั้งสองโหมด (5–7 วัน) — หัวใจของ "อัตโนมัติตั้งแต่ต้นจนจบ"
- `context_onboarding` อ่านผ่าน `source_resolver` (แบบที่ `hierarchy_service` ทำแล้ว) แทน `sqlite3.connect()`
- ลำดับ: เชื่อมต่อ → profile → **ความรู้ที่ประกาศ (ถ้ามี contract)** → อนุมานส่วนที่เหลือด้วย LLM → hierarchy → golden (จากข้อมูล / control totals) → รายงานความพร้อม
- contract เป็น input ที่มีสิทธิ์สูงสุด ไม่ใช่ทางแยก — `datafeed_knowledge` กลายเป็น "ตัวอ่าน contract" ของ pipeline
- **Exit — พิสูจน์ว่ารองรับสองโหมดจริง:** onboard `feed_revenue` สองครั้งบน source เดียวกัน — ครั้งแรก**ใช้** contract,
  ครั้งที่สอง**ปิด**การอ่าน contract (อนุมานล้วน) → ทั้งคู่ได้ครบ 7 ตาราง, วัดด้วยชุดคำถามจริงชุดเดียวกัน;
  โหมดอนุมานคาดว่าได้คะแนนต่ำกว่าและมีคิวยาวกว่า — **ตัวเลขช่องว่างนั้นคือมูลค่าของ contract** ที่บอกลูกค้าได้

### 8.3 — คิวตัดสิน + รายงานความพร้อม (3–5 วัน)
- คิวรวม: การอนุมานที่ไม่มั่นใจ · ข้อขัดแย้งระหว่างช่องทาง · คำที่ไม่รู้จัก · คำถามจริงที่ได้ 0 แถว / ล้ม / ถูกปฏิเสธ
- รับ / แก้ / ปฏิเสธ → กลายเป็น `manual`
- รายงานความพร้อมต่อ context: ครอบคลุม 7 ตารางแค่ไหน · คะแนนจากคำถามทดสอบ · รายการที่ยังค้าง → **gate "พร้อมเปิดให้ผู้ใช้"**
- **Exit:** ชุดข้อมูลใหม่ไปถึง "พร้อม" ได้โดยไม่มีใครแตะตาราง config หรือ SQL โดยตรง

### 8.4 — Connector: อ่าน ณ ที่อยู่ (ทีละชนิด)
ทุกตัวทำ interface เดียวกัน: list ตาราง/คอลัมน์ · profile · SELECT ที่ถูกบังคับ scope · ความสด (`data_as_of`) · fail closed
→ scope / `llm_data_policy` / audit / onboarding (8.2) ทำงานเหมือนเดิมโดยไม่แก้
1. CSV / Excel ทั่วไป (ไม่มี manifest / contract) — ใช้ DuckDB เดิม; ความรู้มาจาก 8.2 ล้วน
2. Postgres / SQL Server แบบ read-only (login เฉพาะ + GRANT เฉพาะ schema ที่เปิด — `PLAN_7` §6.5)
3. S3 / HTTPS bundle (`PLAN_7` §13 ออกแบบไว้แล้ว)
4. REST API — ภายหลัง (ข้อตัดสิน D-F)
- **Exit ต่อตัว:** onboarding 8.2 + scope + policy + audit ผ่านโดยไม่แก้ชั้นบน

### 8.5 — บริการของ tenant: key, BYOK, เอกสาร, ช่องทาง (4–6 วัน)
- **ที่เก็บ secret แบบเข้ารหัสตัวเดียว** ใช้ร่วมทั้ง credential ของ source (8.4) และ key ของ LLM — ไม่ส่งกลับทาง API, ไม่ลง log,
  ทดสอบด้วย call จริงก่อนบันทึก (วันนี้ไม่มีการเข้ารหัส secret ที่ใดในระบบ)
- **BYOK ต่อ workspace** — `_build_provider_kwargs` หา key ของ workspace ก่อน → key ของแพลตฟอร์ม (ถ้าอนุญาต) → ไม่มี;
  ทำงานร่วมกับ `llm_provider_allowlist` ของ source; ใช้ key ของใคร = นับโควตา/ต้นทุนให้คนนั้น
- **API key แบบ self-service** — ลูกค้าออก / หมุน / เพิกถอน key ของ workspace ตัวเอง (ใช้ `APIKeyService` + การผูก workspace ที่มีอยู่)
- **เอกสาร API สาธารณะ** — spec ที่มีเฉพาะ `/api/v1/query*` + `/api/v1/mcp` + quick start; หน้าตั้งค่า Claude Desktop (bridge มีแล้ว)
- **web chat ต่อ workspace** — วันนี้ `chat.py` ไม่รู้จัก workspace
- **Exit:** ลูกค้าคนหนึ่ง**ไม่ต้องพึ่ง admin**: ต่อ source → พร้อม → ออก key → ใส่ key LLM ของตัวเอง → ถามผ่าน web, REST และ Claude Desktop ได้ครบ

### 8.6 — สมัครใช้เอง (สวิตช์สุดท้าย — ขึ้นกับ D-A)
- สมัคร = สร้าง user + workspace · โควตาเริ่มต้น · กันการใช้ในทางที่ผิด · ข้อตกลง / ความยินยอม PDPA

## 9. ข้อเสนอ: เครื่องมือทำ contract ให้เจ้าของข้อมูล (2026-09-23 — รอเจ้าของตัดสิน D-G)

**ที่มา:** งานถามข้ามรายงาน (EBT → ค่าใช้จ่าย / ยอดขาย). การกระทบยอด 19 งวดด้วยมือ (`plan/PROMPT_NT_REPORT_EBT_EXPENSE.md`) พบ
ความสัมพันธ์ 2 เส้นที่ contract ไม่มี — เส้นหนึ่ง contract ประกาศผิดว่า "ห้ามเทียบ" (`ebt_sales_base_vs_sales_dw`) ทั้งที่ตรงทุกสตางค์ —
และพบ ebt feed ที่ build ก่อนไฟล์ต้นทางชุดใหม่ (202606 ต่าง 51.10 M). NT-Report แก้ครบในรอบเดียว (ebt 1.4.3 / expense 1.2.3 /
sales 1.3.3 + ตรวจ bridge ทุก build — `manifest.reconcile.bridges`) → **งานนี้เป็นเครื่องมือได้ และ contract ที่คนเขียนเองก็พลาด**

### 9.1 ข้อเสนอ
เจ้าของข้อมูลบอกจุดเชื่อมต่อ → เลือก DB / ตาราง / ไฟล์ → ระบบร่าง contract → เจ้าของตอบเฉพาะข้อที่ระบบไม่แน่ใจ → ยืนยัน →
contract ที่มีเวอร์ชันเข้า pipeline เดิม. **ผลลัพธ์คือ contract ไฟล์เดียว รูปแบบเดียวกับของ NT-Report — ไม่ใช่ช่องทางใหม่:**
8.2 อ่าน contract อยู่แล้ว (input ที่มีสิทธิ์สูงสุด); เครื่องมือนี้คือตัวอนุมานของ 8.2 ที่เขียนผลเป็น**ร่าง contract** แทนเขียนลงตารางตรง ๆ
และคือคิวของ 8.3 ในมุมของเจ้าของข้อมูล — คำยืนยันของเจ้าของ = `declared`

| ส่วนของ contract | ร่างจากข้อมูลอย่างไร (ตรวจใน code ไม่ใช่ LLM) | ตัวอย่างจาก NT-Report |
|---|---|---|
| dataset · คอลัมน์ · dtype · key · grain | profile + ทดสอบความ unique | `fact_expense` = GL × cost center × เดือน |
| `agg`: sum / point_in_time | ค่าเพิ่มทุกงวดแล้วรีเซ็ตต้นปี = ยอดสะสม (ห้าม SUM ข้ามงวด) | `expense` ของ ebt, `revenue_ytd` |
| คอลัมน์แยกสถานการณ์ | คอลัมน์ค่าน้อยที่แบ่ง measure เป็นก้อนขนาดใกล้กัน = ห้ามรวม | `metric` actual / target |
| hierarchy | functional dependency | สายงาน → ฝ่าย → ส่วน |
| `control_totals` · `scope_columns` | ยอดรวมรายงวด · คอลัมน์งวด / หน่วยงาน | มีใน contract ทุกโดเมน |
| **`relationships` (ใหม่)** | key ร่วม + กระทบยอดรายงวดด้วยตัวกรองที่เป็นไปได้ → งวดที่ตรง / ไม่ตรง + ยอดต่าง เป็นหลักฐาน | ebt ↔ expense (ไม่รวม ER), ebt ↔ sales (`sales_line`, BG 1–7) |
| คำอธิบายภาษาไทย · คำพ้อง | LLM จากชื่อคอลัมน์ (+ ค่าตัวอย่างเฉพาะ source ที่ policy = `full`) | — |

**ต้องถามเจ้าของเท่านั้น:** ความหมายทางธุรกิจ · ข้อยกเว้น (EBT ตัด ER) · เหตุของความผิดปกติที่เครื่องเจอ (202606) — เครื่องแปลงเป็นคำถามให้

**ใช้ง่าย:** เจ้าของไม่เห็น YAML / SQL — เห็นคำถามภาษาไทยพร้อมหลักฐาน (ใช่ / ไม่ใช่ / แก้) · รับเองเฉพาะข้อที่พิสูจน์ด้วยตัวเลขได้
(ยังแสดงให้เห็น) · เรียงตามผลกระทบ จำกัดต่อรอบ (§7) · ก่อนยืนยันแสดงคำถามทดสอบพร้อมตัวเลขให้เทียบกับรายงานของเจ้าของ (D-E) ·
ข้อมูลเปลี่ยน → diff → ถามเฉพาะที่เปลี่ยน · ส่งออก YAML ได้ (เจ้าของเก็บใน repo ตัวเองแบบ NT-Report) ·
เจ้าของที่มี contract อยู่แล้ว: เครื่องมือ**ตรวจ** contract กับข้อมูล (ความสัมพันธ์ที่ขาด, ข้อที่ขัดกับตัวเลข) แล้วรายงาน — ไม่แก้ contract เอง
